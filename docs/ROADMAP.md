## Sprint 2.5 — Schema Review ✅

- Two rounds of critical simplification against "one developer should understand the whole schema in one sitting": 8 tables → 3 tables → 2 tables (`destinations`, `venues`), folding regions/districts/aliases/boundaries/categories/beaches into plain columns (text, arrays, JSONB) wherever a full table wasn't earning its cost.
- Settled primary-key strategy (preserve existing stable source IDs rather than UUIDs or new surrogate keys), a flat fixed category list, a simple two-column image model, and JSONB opening hours.
- **Product decision**: the platform will not be live-edit. Introduced the draft → publish architecture — `destinations`/`venues` are the private editorial working tables; a new `publish_revisions` table (immutable, whole-dataset JSONB snapshots) is the only thing the public site reads, with instant rollback to any previous revision. Updated `PRODUCT.md`, `ARCHITECTURE.md`, `DATABASE.md`, and `API.md` to reflect it.
- Final schema: **3 tables** (`destinations`, `venues`, `publish_revisions`). Design only — no SQL, no migrations.

## Sprint 6 — Venue Explorer ✅

- Built the first real Studio feature: a live Venues list. `src/lib/apiClient.ts` (fetch wrapper), `src/types/venue.ts`, and `src/features/venues/` (`api.ts`, `useVenues.ts` — a TanStack Query hook, `VenueTable.tsx`) fetch from `GET /venues` and display Name, Category, Destination, Status. - **Required backend change**: added CORS middleware to `api/app/main.py` (GET-only, `localhost:5173`/`127.0.0.1:5173`) — without it the browser blocks Studio's requests to the API outright, since they're different origins. Infrastructure, not a feature.
- **Found and fixed a real bug during verification**: the page initially used `isLoading` to gate the loading state, which in TanStack Query v5 is only true *during active fetching* — between retry attempts there's a pending-but-not-fetching gap where a fetch failure was misread as "no data" and showed the empty state instead of loading. - **Diagnosed and deliberately did not "fix" a second issue**: in this automated browser test environment, `document.visibilityState` is permanently `"hidden"` (a standard headless-browser characteristic), which makes TanStack Query pause retries indefinitely via its `focusManager` — a real, intentional feature for real users (don't burn retries on a backgrounded tab), not an app bug. Verified this was the true cause by reading the library's source directly, then confirmed the error state renders correctly by forcing `visibilityState` for the test session only (never shipped). Also set `networkMode: 'always'` globally as independent, legitimate defense against unreliable `navigator.onLine` reporting.
- Verified all four states in-browser against the real Supabase-backed API: loaded (seeded venue), loading, error (API stopped — "Failed to fetch" + working "Try again" that recovers), and empty (temporarily stubbed, reverted after). Build and lint clean, no console errors.
- Business logic (status meaning, data validity) stays in the API; the frontend only fetches and displays. `destination_id` is shown as-is (e.g. `"marassi"`) since the API doesn't yet return a resolved destination name — noted as an API-side concern for later, not something to join client-side now.

## Sprint 10 — Draft State Management ✅

- Extracted Sprint 9's inline mode/draft `useState` calls in `VenueWorkspace` into a generic `useDraft<T>` hook (`src/hooks/useDraft.ts`, not venue-specific) — the sprint explicitly frames this as "the draft workflow future Save and Publish will use," which is a signal to generalize now rather than hardcode into one component.
- **Dirty detection**: `isDirty = JSON.stringify(draft) !== JSON.stringify(original)`, computed inside the hook. Simple and correct without hand-maintaining a per-field diff list that would need updating every time a new editable field is added.
- **Unsaved changes indicator**: an amber "Unsaved changes" pill in `WorkspaceToolbar`, shown only when `mode === 'edit' && isDirty`.
- **Cancel restores original data**: unchanged behavior from Sprint 9, reverified.
- **Switching venues while dirty asks for confirmation**: `VenueWorkspace` reports `isDirty` up to `Venues.tsx` via a plain `onDirtyChange` callback (not by lifting the whole draft/venue-fetching structure) — "should switching venues warn" is a page-level concern spanning the list and the workspace, and `Venues.tsx` is their common ancestor. `Venues.tsx` wraps venue selection with `window.confirm(...)` when dirty.
- **Browser refresh protection while dirty**: `useDraft` self-registers a `beforeunload` listener whenever `isDirty` is true (removed when it isn't) — baked into the hook itself, so any future entity workspace built on `useDraft` gets this for free.
- **Explicitly out of scope, noted rather than silently skipped**: route-level navigation (e.g. clicking "Destinations" in the sidebar while a venue edit is dirty) is not guarded — only same-page venue switching and browser refresh/close, matching exactly what this sprint asked for.
- Verified in-browser against the real Supabase-backed API, including cases that are easy to get wrong: the indicator only appears once a field actually changes (not immediately on entering Edit Mode); declining the venue-switch confirmation correctly keeps the current edit intact and selected; confirming it discards the edit and switches; the discarded venue's real data is provably unaffected on revisiting it; and the `beforeunload` handler's `defaultPrevented` was confirmed `true` while dirty and `false` immediately after Cancel, by dispatching a real `beforeunload` event, not by reading the code and assuming. No non-GET requests were ever sent. Build and lint clean, no console errors.

## Sprint 11 — Save Draft ✅

The first write operation. Not Publish — Save Draft only, writing straight to the draft `venues` row with no status change.

- **Backend**: added `PATCH /venues/{venue_id}` (`api/app/api/routes/venues.py`) and a `VenueUpdate` Pydantic schema (`api/app/api/schemas.py`) covering exactly the fields Edit Mode already exposes as editable (`name`, `category`, `district`, `is_featured`, `is_verified`, `short_description`, `latitude`, `longitude`, `maps_url`, `phone`, `whatsapp`, `website`, `instagram_handle`, `facebook_handle`, `tiktok_handle`, `internal_notes`). Applies only the fields present in the request (`.model_dump(exclude_unset=True)`), commits, and returns the updated venue through the same enriched `VenueOut` shape (with `destination` eager-loaded) as the `GET` endpoints — the frontend gets one consistent Venue shape everywhere. `404` for an unknown venue id. Added `PATCH` to the CORS `allow_methods` alongside `GET`.
- **Frontend**: `apiClient.ts` gained `apiPatch`. `features/venues/api.ts` gained `updateVenue(id, patch)` and `toVenuePatch(venue)` — the latter picks only the editable fields and normalizes cleared text inputs (`''`) to `null` to match the API's nullable columns, rather than sending a literal empty string. A new `useUpdateVenue` hook wraps this in a TanStack Query `useMutation`; on success it writes the server's response into both the `['venue', id]` and `['venues']` caches directly (`setQueryData`), rather than trusting the client's own draft or issuing a refetch — the server's response is the source of truth for what was actually persisted (e.g. any future server-side normalization).
- **`useDraft` gained `commitSave(saved)`**: sets both `draft` and `baseline` to the server's response, which resets `isDirty` to `false` without touching `mode` — this is the mechanism behind "stay in Edit Mode after Save," as distinct from `cancelEditing()` which drops back to `'view'`.
- **`WorkspaceToolbar`** gained a `Save Draft` button (with a spinner while saving) next to Cancel in Edit Mode, disabled whenever `!isDirty || isSaving` — per the "disable Save Draft when there are no changes" requirement — plus an inline error message when a save fails. `VenueWorkspace` wires `onSave` to call the mutation with `toVenuePatch(displayedVenue)` and `commitSave` as its `onSuccess` callback, and clears any stale save error on Cancel.
- **Explicitly not implemented, per instruction**: Publish, autosave, field-level validation, revision creation, rollback, authentication. The PATCH endpoint accepts whatever Pydantic's type coercion allows — no required-field checks, no category/coordinate sanity checks. That's the "Validate" workflow step, a deliberately separate, not-yet-built gate between `draft` and `review` (see [`DATABASE.md`](DATABASE.md#editorial-status-one-shared-vocabulary-renamed-to-avoid-colliding-with-the-new-meaning-of-publish)).
- Verified against the real Supabase-backed API, both via direct `curl` (successful PATCH, 404 on an unknown id, a temporary second venue added and removed the same way Sprint 7 verified switching) and in-browser: editing and saving a field persists it (confirmed via a fresh API request and a hard page reload, not just re-reading client state), the toolbar returns to a clean not-dirty state and **stays in Edit Mode** afterward, Cancel after a successful save reverts to the *saved* value (not the pre-save one) since the baseline moved, stopping the API mid-edit and clicking Save Draft shows an inline error while preserving the in-progress draft untouched, and retrying the same save once the API is back up succeeds. Switching to a different venue immediately after a successful save (dirty now `false`) does not trigger the Sprint 10 unsaved-changes confirmation. Database restored to the exact Sprint 4 seed state after verification. Build and lint clean, no console errors.

**Technical debt / follow-ups noted, not fixed this sprint**:
- Save Draft always sends every editable field, not a diff of only the fields that actually changed — simpler and correct given `useDraft`'s whole-object model, but a larger PATCH body than strictly necessary. Worth reconsidering only if payload size or partial-conflict semantics become a real concern.
- No optimistic update — the UI waits for the server's response before clearing the dirty indicator. Deliberate: matches "handle loading state" from this sprint's requirements, and avoids the class of bugs where an optimistic update has to be rolled back on failure.
- The failed-save error message is generic (the underlying `ApiError`'s message, or a fallback string) — no error-code-specific messaging yet, since there is no validation step producing structured errors to distinguish.

## Sprint 12 — Validation ✅

Implements the "Validate" gate described in `docs/DATABASE.md`, per an explicit architectural instruction: validation is split into two independent layers that share no business logic — frontend UX validation (instant feedback, generic, reusable) and backend canonical validation (the actual source of truth). Nothing here changes `status` or moves a row toward Review — that transition still doesn't exist.

- **Backend**: new `api/app/validation/` package, deliberately generic so it isn't a Venue-only concept:
  - `schemas.py` — `FieldError {field, message}` and `ValidationResult {valid, errors}`. One reusable response contract; a future `validate_destination()` returns the exact same shape.
  - `venues.py` — `validate_venue(venue)`, the **canonical** rule set and the only place these rules are enforced: `name` non-blank, `category` in the documented `VENUE_CATEGORIES` (already DB-enforced by a `CHECK` constraint, but re-checked here for a structured error instead of a raw constraint violation), and `latitude`/`longitude` within the observed North Coast range (`[30.6, 31.1]` / `[28.6, 29.4]`) — a sanity bound per `DATABASE.md`, not a DB constraint.
  - New route `POST /venues/{venue_id}/validate` (`api/app/api/routes/venues.py`) — reads the venue's **currently persisted** row (not a request body — there's nothing to submit) and returns its `ValidationResult`. Read-only, `404` on an unknown id. Added `POST` to the CORS `allow_methods`.
  - Save Draft (`PATCH /venues/{venue_id}`) is **unchanged** — it still accepts anything Pydantic's type coercion allows, no business-rule enforcement. This is deliberate, not an oversight: `docs/DATABASE.md` frames Validate as a distinct workflow step between Save Draft and Review, not something Save Draft itself gates on — a draft is allowed to be incomplete.
- **Frontend, generic layer** (`src/lib/validation.ts`): `isRequired`, `isWithinMaxLength`, `isValidUrl`, `isValidDecimal`, and a `runFieldRules(value, rules)` combinator — entity-agnostic primitives with no opinion about what makes a *venue* valid, so any future entity's edit form reuses them without touching this file.
- **Frontend, venue-specific field selection** (`features/venues/venueValidation.ts`): `validateVenueDraft(venue)` applies the generic primitives to specific fields — `name` required, `short_description`/`internal_notes` length-capped, `website`/`maps_url` URL-shaped, `latitude`/`longitude` numeric-shaped. Deliberately excludes category membership and geographic coordinate bounds — those are business rules, and duplicating them here would mean two sources of truth for the same rule, which the architectural instruction explicitly ruled out.
- **Inline field errors**: `FieldLabel` gained an `error?` prop (renders red text under the input); a new `fieldStyles.ts` (extracted out of `FieldLabel.tsx` to avoid a react-refresh lint warning from mixing component and non-component exports) provides `fieldInputClassName(hasError)` for the red-border state. `TextField`/`TextAreaField` accept an `error?` prop; `SelectField`/`CheckboxField` don't, since nothing validated this sprint uses them. Every workspace section (`BasicInfoSection`, `LocationSection`, `ContactSection`, `PublishingStatusSection`) now accepts an `errors?: FieldErrors` prop and threads the relevant key to each field.
- **Save Draft gating**: `VenueWorkspace` computes `fieldErrors = validateVenueDraft(displayedVenue)` while in Edit Mode and disables Save Draft whenever any exist, alongside the existing `!isDirty || isSaving` conditions — per "enable/disable Save Draft" being an explicit frontend-validation responsibility.

## Sprint 16 — Publish Engine ✅

Creates the first immutable published revision. No Rollback, no revision browsing/history — only the publishing engine itself, per instruction.

- **Backend**, new `api/app/publishing/` package — deliberately separate from `app/validation/` and `app/workflow/`, since Publishing is a snapshot operation, not a status change or a status-transition guard:
  - `engine.py`'s `publish(db)`: queries every `destinations`/`venues` row currently `status = approved`, serializes each into a lean, JSON-native dict (Decimal columns stringified; `status` and editorial-only fields like `internal_notes`/timestamps omitted — nothing here is meant for public consumption), and writes both arrays into one `publish_revisions.snapshot` JSONB row. In the **same transaction**: flips any existing `is_current = true` row to `false`, then inserts the new row with `is_current = true`, then commits once — so the pointer move is atomic (backed further by the Sprint 3 partial unique index on `is_current`). Also stamps `last_published_at` on every published row — a field `docs/DATABASE.md` designed for exactly this back in Sprint 2.5, unused until now.
  - `engine.py`'s `get_current_revision(db)`: the *only* lookup a public read path is allowed to use — looks up the row where `is_current = true`, nothing else.
  - Never reads or writes `destinations.status`/`venues.status` anywhere in this package — Approval (Sprint 15) already decided eligibility; Publish only freezes it.
- **New endpoints** (`api/app/api/routes/publish.py`):
  - `POST /publish` — no request body, runs the engine, returns `PublishRevisionOut` (id, `is_current`, `published_at`, counts) — metadata, not the full snapshot.
  - `GET /published/venues` — the first real **public read path**. Resolves each snapshot venue's `destination_id` against the *same snapshot's* destinations array (no DB query at all) and returns `PublishedVenueOut`, a leaner shape than the draft `VenueOut` (no `status`, no editorial-only fields). Returns `[]` if nothing has ever been published.
- **New schemas** (`api/app/api/schemas.py`): `PublishRevisionOut`, `PublishedVenueOut`.
- Verified against the real Supabase-backed API:
  - **approved → published revision**: `POST /publish` with the seeded (already-`approved`) destination/venue → `{id: 1, is_current: true, destination_count: 1, venue_count: 1}`; `GET /published/venues` immediately returned the venue with its destination correctly resolved.

  - Build and lint clean, no console errors (no frontend changes this sprint — Publish has no Studio UI yet, per the absence of a Frontend section in this sprint's instructions).

**Why publishing is snapshot-based**: a live `WHERE status = 'approved'` query at read time can't answer "what did the site look like before this change," and it couples the public read path's correctness/availability to whatever the draft tables are doing at that instant. A snapshot is a complete, self-contained copy — `GET /published/venues` never queries `Destination`/`Venue` at all, so draft-table writes can never affect it, and a past revision is a faithful copy of what was actually live, not a reconstruction from current data.

**Why immutable revisions exist**: nothing in this codebase ever updates or deletes a `publish_revisions` row after it's inserted — a new publish always *adds* a row and moves the pointer. This is what makes "the site looked like this on this date" a trustworthy claim rather than an approximation, and it's what a future Rollback needs to be meaningful: rolling back only works if the target revision is guaranteed untouched since it was current.

**How Rollback will reuse this infrastructure**: everything it needs already exists — multiple immutable revisions coexist, and the atomic "exactly one `is_current`" pointer-flip pattern is already proven in `publish()`. Rollback will be almost exactly half of that function, run in reverse: flip the currently-current revision to `false` and flip a *chosen past* revision to `true`, in one transaction. No new snapshot logic, no new schema — just a different source for which row becomes current.

**Technical debt / follow-ups noted, not fixed this sprint**:
- No Rollback endpoint — deliberately out of scope, per instruction; the infrastructure it needs is in place (see above).
- No revision-history/browsing endpoint (e.g. `GET /publish-revisions`) — deliberately out of scope, per instruction. Would need no new mechanism, just a new query returning a list of `PublishRevisionOut`.
- **Known snapshot edge case, not exercised by current data**: `publish()` requires a venue's own `status` to be `approved` but doesn't require its `destination` to also be `approved`. If that ever diverges, `GET /published/venues` silently skips the orphaned venue (no destination name to resolve from the snapshot) rather than raising — reasonable defensive behavior, but the underlying question ("should an approved venue publish at all if its destination hasn't been approved") is a real product decision this sprint didn't need to make, since the seed data's destination and venue are both `approved`.
- No `GET /published/destinations` companion endpoint — not needed for this sprint's verification, since `PublishedVenueOut` already embeds the resolved `{id, name}` a public consumer needs; would follow the exact same pattern if a future page needs a bare destinations list.
- The full public/editorial endpoint split (`docs/API.md`'s long-open item) is still only partially real: `GET /published/venues` is genuinely public-only, but `GET /venues`/`GET /destinations` still read the draft tables directly with no auth gate — unchanged from every prior sprint, not addressed here.

**Why revision history exists**: immutability (Sprint 16) only matters if it's something an editor can actually observe — without a way to look at past revisions, "we never overwrite history" would be true but invisible, indistinguishable from not having history at all. The Revision Browser makes that guarantee concrete: an editor can see, right now, that revision 4 and revision 5 are both still there, unchanged, exactly as published.

**Why Rollback is intentionally not part of this sprint**: reading history and changing what the public site currently serves are different risk classes — one is side-effect-free and safe to ship immediately, the other is a real, live-affecting write that deserves its own deliberate design (confirmation UX, an eventual audit trail once auth exists). This sprint deliberately solves only the "can an editor find and understand a past revision" half of Rollback's UX, so that when Rollback is actually scoped, its only new work is the restore transaction itself — reusing this same list and detail view, not reinventing the discovery step alongside it.

**Technical debt / follow-ups noted, not fixed this sprint**:
- No Rollback action anywhere — deliberately out of scope, per instruction. The read-only pieces it will need (list + detail) are exactly what this sprint built.
- The "snapshot summary" in `RevisionDetail` shows only name/region for destinations and name/category for venues — deliberately lean, not the full per-field record (that's what `GET /publish/revisions/{id}`'s raw `snapshot` already provides, and a raw JSON dump in the UI wasn't asked for). Worth revisiting only if a future need (e.g., comparing two revisions field-by-field) requires more detail than this summary shows.
- `RevisionField.tsx` duplicates `WorkspaceField.tsx`'s exact shape (label/value pair with a placeholder) in a second location — a deliberate choice to avoid a cross-feature import for one small presentational atom, not an oversight. If a third feature needs the same shape, that's the trigger to promote it into `src/components/`, not before.

## Sprint 18 — Republish Revision ✅

Lets an editor make an existing published revision current again — the Rollback mechanism Sprint 16/17 flagged as future work, built here under the name Republish. No snapshot is created, regenerated, or edited; only the `is_current` pointer moves.

- **Backend** (`api/app/publishing/engine.py`): new `republish(db, revision_id)` — fetches the target revision (`404` if missing), rejects with `409` (`error: "already_current"`) if it's already current, then flips the old current to `false` and the target to `true` in one transaction, same atomic pattern `publish()` already used. **Never queries `Destination`/`Venue`, never touches any revision's `snapshot`/`published_at`/counts** — verified directly by republishing a revision and confirming its `published_at` stayed byte-identical to its original publish timestamp.
- **New route** (`api/app/api/routes/publish.py`): `POST /publish/revisions/{revision_id}/republish`, returning the republished revision as `PublishRevisionOut` (metadata only — same shape `POST /publish` already returns).
- **Frontend**: `api.ts` gained `republishRevision(id)`; a new `useRepublishRevision` mutation invalidates both the `['publish-revisions']` list query and the `['publish-revision']` detail query prefix on success — a full refetch rather than a targeted cache patch, since republishing changes `is_current` on *two* rows (the old current and the new one), which a single-entry cache update can't keep consistent for every previously-viewed revision. `RevisionDetail.tsx` gained a blue "Republish" button, shown only when `!revision.is_current`, plus an inline error message reusing the same `ApiError`-aware pattern the Venue Workspace's action buttons already established.
- Verified against the real Supabase-backed API (published the seeded data twice with a draft edit in between, producing two distinct revisions, same approach as Sprint 17) and in-browser:
  - **Old revision becomes current**: republished the older of the two revisions — response showed `is_current: true`, with its `published_at` unchanged from the original publish.
  - **Current revision becomes non-current**: the list confirmed the previously-current revision flipped to `is_current: false` in the same call — both changes are one atomic operation, not two separate ones a client could observe half-applied.
  - **Multiple revisions remain unchanged**: fetched both revisions' full detail after republishing — each snapshot still showed its own original venue name (`"The Smokery"` vs `"The Smokery (Updated)"`), and `GET /published/venues` correctly followed the pointer to whichever revision was now current.
  - **404 / 409**: an unknown revision id → `404`; republishing the already-current revision a second time → `409` with the structured `already_current` detail.
  - **In-browser**: selected the non-current revision, confirmed the "Republish" button appeared (and was absent on the current one), clicked it, confirmed the list's "Current" badge moved to the just-republished revision and the detail header updated to show "Current" — both the list and detail refreshed automatically via the mutation's cache invalidation, with no manual refresh needed. Re-selected the now-non-current revision and confirmed its Republish button reappeared there instead.
  - **Hard refresh**: force-reloaded the Publishing page after republishing — the correct revision was still marked current, confirming the change is real and persisted, not a client-side-only cache effect.
  - Restored the database fully afterward: deleted both test `publish_revisions` rows (table was empty before this sprint, consistent with every prior sprint's cleanup), reverted the draft venue's name, and cleared both rows' `last_published_at` timestamps.
  - Build and lint clean, no console errors.

**Why republishing is safer than rewriting history.** The tempting alternative — reconstruct the old data and run a normal publish again — would require either resurrecting past draft content (impossible without disturbing whatever the drafts currently hold) or mutating an old revision's snapshot to make it "publishable" again. Republish does neither: it never reads or writes `destinations`/`venues`, never reconstructs anything, and never touches a snapshot's bytes. The only thing that changes is which single row has `is_current = true` — the smallest, most reversible operation that could achieve "make the site show what it showed before."

**Why snapshots remain immutable.** It would have been easy to let Republish "refresh" the target revision's `published_at` to mark when it became current again — Sprint 18 deliberately doesn't. A revision's stored data staying exactly as first published, even through a republish, is what makes every future republish of that same revision guaranteed to produce identical results. Immutability isn't just a Sprint 16 property that happened to survive to Sprint 18 unchanged — this sprint is direct proof that even the "restore an old state" action doesn't need to compromise it.

**Technical debt / follow-ups noted, not fixed this sprint**:
- No confirmation step before republishing — clicking the button acts immediately. Given the operation's low risk (reversible by republishing the other revision back, and no data is ever lost), this felt proportionate for this sprint's scope; worth reconsidering if Rollback later gains more ceremony (an audit trail, multi-revision diff preview) that would make a confirmation step meaningful rather than just friction.
- `useRepublishRevision`'s cache invalidation is a full refetch of every cached revision, not a precise two-row patch — simpler and correct, but marginally more network traffic than a hand-computed cache update would need. Not worth the complexity at this data volume (a handful of revisions).
- Republish still has no audit trail (who republished, when, from which previous current) — flagged as a natural extension once authentication exists, not part of this sprint's scope.

## Sprint 19 — Editorial Activity Log ✅

A centralized, cross-cutting record of editorial actions. Observability only — nothing here changes what any workflow/publishing action does.

- **Schema**: new `activity_log` table (`api/app/db/models.py`'s `ActivityLogEntry`, migration `api/alembic/versions/0002_activity_log.py` — the first schema change since Sprint 3). Columns: `id`, `timestamp`, `action`, `entity_type`, `entity_id` (always text, even for `publish_revisions`' integer ids — a shared column for references to differently-typed entities), `actor` (default `'system'`), and `metadata` (nullable JSONB). No foreign keys in or out, same reasoning as `publish_revisions`: a log entry is a point-in-time record, not a live reference to a row that might later change or disappear. The Python attribute for the metadata column is named `activity_metadata`, not `metadata` — `metadata` is reserved on every SQLAlchemy declarative model (it's `Base.metadata`, the schema's own `MetaData` instance) — mapped to the actual `metadata` column/JSON field name via an explicit column-name argument.
- **Backend service** (`api/app/activity/service.py`) — a new package, deliberately independent of `validation/`, `workflow/`, and `publishing/`: `log_activity()` is the one function that ever constructs an `ActivityLogEntry`, and it does not commit — callers `db.add()` it within their own existing transaction, so an activity entry and the action it describes are always persisted atomically together, never one without the other. `PLACEHOLDER_ACTOR = "system"` is the module-level constant every call site currently relies on, since no authentication exists yet.
- **Wired into all four actions, no duplicated logging logic**:
  - `submit_venue_for_review` and `approve_venue` (`api/app/api/routes/venues.py`) each call `log_activity()` once, right before their existing `db.commit()`.
  - `publish()` (`api/app/publishing/engine.py`) calls it after `db.flush()` (needed to get the new revision's id before logging it) but still before `db.commit()`, with `metadata={"destination_count": ..., "venue_count": ...}`.
  - `republish()` (same module) calls it right before its own `db.commit()`, with no extra metadata (the target revision's id is already the `entity_id`).
- **New endpoint**: `GET /activity` (`api/app/api/routes/activity.py`), returning every `ActivityLogEntryOut` newest-first. Read-only — this route, and this entire feature, never write anything.
- **Frontend**: a new `features/activity/` — `useActivity` (a single read-only TanStack Query hook, no mutation anywhere in the feature), `ActivityTable` (a flat table: Timestamp, Action — human-readable via a small label map, falling back to the raw string for anything not yet listed — Entity, Metadata as inline JSON), and `ActivityPanel` (loading/error/empty + the table). `pages/Activity.tsx` is a single-panel page (no list/detail split — there's nothing to select, just a feed) wired into `App.tsx`'s routes and `config/navigation.ts`'s sidebar.
- Verified against the real Supabase-backed API: ran the migration live (`alembic upgrade head`, confirmed `0001 → 0002`), inspected the resulting `activity_log` table's columns directly via SQLAlchemy's inspector to confirm the schema matched. Exercised all four actions in sequence (flipped the seeded venue to `draft` via a direct DB session, `submit-for-review` → `approve` → `publish` → edited the draft and `publish` again → `republish` the earlier revision) and confirmed `GET /activity` returned exactly five entries, newest-first, with the correct `action`/`entity_type`/`entity_id`/`metadata` for each. In-browser: navigated to the new Activity page, confirmed all five rows rendered with human-readable action labels and correctly-formatted timestamps, and confirmed a hard refresh reproduced the same list (fetched fresh, not cached). Database restored fully afterward: deleted the test `publish_revisions` and `activity_log` rows, reverted the venue's name/status and both rows' `last_published_at` timestamps. Build and lint clean, no console errors.

**Why activity logging is infrastructure rather than workflow**: every logged action has already fully decided its own outcome (Review's readiness gate, Approval's status guard, Publish's eligibility filter, Republish's already-current check) before `log_activity()` is ever called — logging happens strictly after success, and nothing about it can affect whether an action succeeds or what state a row ends up in. A workflow step decides what happens next; this only ever records what already happened. That asymmetry is what keeps it a cross-cutting concern rather than a fifth workflow concept sitting alongside Validation/Workflow/Publishing.

**How future users/roles will integrate with it**: the `actor` column and `log_activity()`'s `actor` parameter already exist specifically to receive this without any further schema change — every call site currently passes the default `PLACEHOLDER_ACTOR`, but swapping in a real authenticated user's identifier once auth exists is a one-line change per call site, not a new column, table, or endpoint. Roles/permissions (who's *allowed* to take an action) are a separate, later concern from *logging who did* — this sprint only builds the latter, since the former depends on an authentication approach `docs/ARCHITECTURE.md` still lists as an open decision.

**Technical debt / follow-ups noted, not fixed this sprint**:
- No filtering, search, or pagination on `GET /activity` or the Activity page — deliberately out of scope, per instruction ("No filtering yet"). Fine at current volume; worth adding once the log has enough entries that "everything, always" stops being the right default.
- Save Draft and Validate are not logged, on purpose — they don't represent an editorial state transition or a publish event (the four actions the requirements explicitly named), and Save Draft in particular can fire many times per edit session, which would make the log mostly noise rather than a record of what actually changed. Worth revisiting only if there's a real future need for a full edit-history audit trail, which is a different (and larger) feature than this sprint's activity log.
- No index beyond `activity_log(timestamp)` — sufficient for "list everything, newest first"; a future filtered view (by `entity_type`, `entity_id`, or `actor`) would want its own index, added when that query actually exists.

## Sprint 20 — Architecture Hardening Review & Automated Test Infrastructure ✅

Two parts, per instruction: first a comprehensive, chat-only architecture review of Sprints 1–19 (no code changes), then — after approval — this project's first automated test infrastructure. No new application behavior; the only code changes are tests and the tooling to run them.

### Architecture review (no code)

Reviewed backend/database/API/workflow/publishing/activity-logging/frontend/query-cache/error-handling/documentation architecture end to end. Full findings aren't repeated here (they were delivered directly in chat, classified Critical/Recommended/Optional), but the headline conclusions that motivated this sprint's scope:
- **Zero automated tests existed anywhere in the repository** across 19 sprints of business logic — the single highest-leverage gap found.
- The `validation`/`workflow` packages' "reusable for future entities" design goal was unexercised — no second entity has ever used them (destinations have no write path at all).
- Several smaller consistency findings (error-response shape inconsistency between plain-string and structured-dict `detail`, hand-mirrored TypeScript types with no shared generation step, a repeated hand-rolled "async action button" pattern) — all deliberately left unfixed this sprint, since this sprint's instruction was explicitly "protect the existing architecture against regressions," not refactor it.
