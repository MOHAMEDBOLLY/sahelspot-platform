## Sprint 2 — Database Design ✅

## Sprint 2.5 — Schema Review ✅

- Two rounds of critical simplification against "one developer should understand the whole schema in one sitting": 8 tables → 3 tables → 2 tables (`destinations`, `venues`), folding regions/districts/aliases/boundaries/categories/beaches into plain columns (text, arrays, JSONB) wherever a full table wasn't earning its cost.
- Settled primary-key strategy (preserve existing stable source IDs rather than UUIDs or new surrogate keys), a flat fixed category list, a simple two-column image model, and JSONB opening hours.
- **Product decision**: the platform will not be live-edit. Introduced the draft → publish architecture — `destinations`/`venues` are the private editorial working tables; a new `publish_revisions` table (immutable, whole-dataset JSONB snapshots) is the only thing the public site reads, with instant rollback to any previous revision. Updated `PRODUCT.md`, `ARCHITECTURE.md`, `DATABASE.md`, and `API.md` to reflect it.
- Final schema: **3 tables** (`destinations`, `venues`, `publish_revisions`). Design only — no SQL, no migrations.

## Sprint 6 — Venue Explorer ✅

- Built the first real Studio feature: a live Venues list. `src/lib/apiClient.ts` (fetch wrapper), `src/types/venue.ts`, and `src/features/venues/` (`api.ts`, `useVenues.ts` — a TanStack Query hook, `VenueTable.tsx`) fetch from `GET /venues` and display Name, Category, Destination, Status. - **Required backend change**: added CORS middleware to `api/app/main.py` (GET-only, `localhost:5173`/`127.0.0.1:5173`) — without it the browser blocks Studio's requests to the API outright, since they're different origins. Infrastructure, not a feature.
- **Found and fixed a real bug during verification**: the page initially used `isLoading` to gate the loading state, which in TanStack Query v5 is only true *during active fetching* — between retry attempts there's a pending-but-not-fetching gap where a fetch failure was misread as "no data" and showed the empty state instead of loading. Fixed by checking `isPending` instead, which covers the whole pending lifecycle including retries.
- **Diagnosed and deliberately did not "fix" a second issue**: in this automated browser test environment, `document.visibilityState` is permanently `"hidden"` (a standard headless-browser characteristic), which makes TanStack Query pause retries indefinitely via its `focusManager` — a real, intentional feature for real users (don't burn retries on a backgrounded tab), not an app bug. Verified this was the true cause by reading the library's source directly, then confirmed the error state renders correctly by forcing `visibilityState` for the test session only (never shipped). Also set `networkMode: 'always'` globally as independent, legitimate defense against unreliable `navigator.onLine` reporting.
- Verified all four states in-browser against the real Supabase-backed API: loaded (seeded venue), loading, error (API stopped — "Failed to fetch" + working "Try again" that recovers), and empty (temporarily stubbed, reverted after). Build and lint clean, no console errors.
- Business logic (status meaning, data validity) stays in the API; the frontend only fetches and displays. `destination_id` is shown as-is (e.g. `"marassi"`) since the API doesn't yet return a resolved destination name — noted as an API-side concern for later, not something to join client-side now.

- Kept view and edit logic in strictly separate, single-purpose components rather than one component branching internally: `WorkspaceField` (unchanged from Sprint 7, view-only) alongside four new edit-mode atoms in `workspace/fields/` — `TextField` (text/url/tel), `TextAreaField`, `SelectField`, `CheckboxField` — each does exactly one control type and nothing else. Each section picks between the view atom and the matching edit atom per field; only the section knows which control type a field needs (e.g. Category → select), so that decision couldn't live anywhere more generic without guessing.

Also verified switching venues mid-edit correctly drops back to view mode. Build and lint clean, no console errors.

## Sprint 10 — Draft State Management ✅

- Extracted Sprint 9's inline mode/draft `useState` calls in `VenueWorkspace` into a generic `useDraft<T>` hook (`src/hooks/useDraft.ts`, not venue-specific) — the sprint explicitly frames this as "the draft workflow future Save and Publish will use," which is a signal to generalize now rather than hardcode into one component.
- **Dirty detection**: `isDirty = JSON.stringify(draft) !== JSON.stringify(original)`, computed inside the hook. Simple and correct without hand-maintaining a per-field diff list that would need updating every time a new editable field is added.
- **Unsaved changes indicator**: an amber "Unsaved changes" pill in `WorkspaceToolbar`, shown only when `mode === 'edit' && isDirty`.
- **Cancel restores original data**: unchanged behavior from Sprint 9, reverified.
- **Switching venues while dirty asks for confirmation**: `VenueWorkspace` reports `isDirty` up to `Venues.tsx` via a plain `onDirtyChange` callback (not by lifting the whole draft/venue-fetching structure) — "should switching venues warn" is a page-level concern spanning the list and the workspace, and `Venues.tsx` is their common ancestor. `Venues.tsx` wraps venue selection with `window.confirm(...)` when dirty.
- **Browser refresh protection while dirty**: `useDraft` self-registers a `beforeunload` listener whenever `isDirty` is true (removed when it isn't) — baked into the hook itself, so any future entity workspace built on `useDraft` gets this for free.
- **Explicitly out of scope, noted rather than silently skipped**: route-level navigation (e.g. clicking "Destinations" in the sidebar while a venue edit is dirty) is not guarded — only same-page venue switching and browser refresh/close, matching exactly what this sprint asked for.
- Verified in-browser against the real Supabase-backed API, including cases that are easy to get wrong: the indicator only appears once a field actually changes (not immediately on entering Edit Mode); declining the venue-switch confirmation correctly keeps the current edit intact and selected; confirming it discards the edit and switches; the discarded venue's real data is provably unaffected on revisiting it; and the `beforeunload` handler's `defaultPrevented` was confirmed `true` while dirty and `false` immediately after Cancel, by dispatching a real `beforeunload` event, not by reading the code and assuming. No non-GET requests were ever sent. Build and lint clean, no console errors.

## Sprint 11 — Save Draft ✅

The first write operation. Not Publish — Save Draft only, writing straight to the draft `venues` row with no status change.

- **Backend**: added `PATCH /venues/{venue_id}` (`api/app/api/routes/venues.py`) and a `VenueUpdate` Pydantic schema (`api/app/api/schemas.py`) covering exactly the fields Edit Mode already exposes as editable (`name`, `category`, `district`, `is_featured`, `is_verified`, `short_description`, `latitude`, `longitude`, `maps_url`, `phone`, `whatsapp`, `website`, `instagram_handle`, `facebook_handle`, `tiktok_handle`, `internal_notes`). Applies only the fields present in the request (`.model_dump(exclude_unset=True)`), commits, and returns the updated venue through the same enriched `VenueOut` shape (with `destination` eager-loaded) as the `GET` endpoints — the frontend gets one consistent Venue shape everywhere. `404` for an unknown venue id. Added `PATCH` to the CORS `allow_methods` alongside `GET`.
- **Frontend**: `apiClient.ts` gained `apiPatch`. `features/venues/api.ts` gained `updateVenue(id, patch)` and `toVenuePatch(venue)` — the latter picks only the editable fields and normalizes cleared text inputs (`''`) to `null` to match the API's nullable columns, rather than sending a literal empty string. A new `useUpdateVenue` hook wraps this in a TanStack Query `useMutation`; on success it writes the server's response into both the `['venue', id]` and `['venues']` caches directly (`setQueryData`), rather than trusting the client's own draft or issuing a refetch — the server's response is the source of truth for what was actually persisted (e.g. any future server-side normalization).
- **`useDraft` gained `commitSave(saved)`**: sets both `draft` and `baseline` to the server's response, which resets `isDirty` to `false` without touching `mode` — this is the mechanism behind "stay in Edit Mode after Save," as distinct from `cancelEditing()` which drops back to `'view'`.
- **`WorkspaceToolbar`** gained a `Save Draft` button (with a spinner while saving) next to Cancel in Edit Mode, disabled whenever `!isDirty || isSaving` — per the "disable Save Draft when there are no changes" requirement — plus an inline error message when a save fails. `VenueWorkspace` wires `onSave` to call the mutation with `toVenuePatch(displayedVenue)` and `commitSave` as its `onSuccess` callback, and clears any stale save error on Cancel.
- **Explicitly not implemented, per instruction**: Publish, autosave, field-level validation, revision creation, rollback, authentication. The PATCH endpoint accepts whatever Pydantic's type coercion allows — no required-field checks, no category/coordinate sanity checks. That's the "Validate" workflow step, a deliberately separate, not-yet-built gate between `draft` and `review` (see [`DATABASE.md`](DATABASE.md#editorial-status-one-shared-vocabulary-renamed-to-avoid-colliding-with-the-new-meaning-of-publish)).
- Verified against the real Supabase-backed API, both via direct `curl` (successful PATCH, 404 on an unknown id, a temporary second venue added and removed the same way Sprint 7 verified switching) and in-browser: editing and saving a field persists it (confirmed via a fresh API request and a hard page reload, not just re-reading client state), the toolbar returns to a clean not-dirty state and **stays in Edit Mode** afterward, Cancel after a successful save reverts to the *saved* value (not the pre-save one) since the baseline moved, stopping the API mid-edit and clicking Save Draft shows an inline error while preserving the in-progress draft untouched, and retrying the same save once the API is back up succeeds. Switching to a different venue immediately after a successful save (dirty now `false`) does not trigger the Sprint 10 unsaved-changes confirmation. Database restored to the exact Sprint 4 seed state after verification. Build and lint clean, no console errors.

**Technical debt / follow-ups noted, not fixed this sprint**:
- Save Draft always sends every editable field, not a diff of only the fields that actually changed — simpler and correct given `useDraft`'s whole-object model, but a larger PATCH body than strictly necessary. Worth reconsidering only if payload size or partial-conflict semantics become a real concern.
- No optimistic update — the UI waits for the server's response before clearing the dirty indicator. Deliberate: matches "handle loading state" from this sprint's requirements, and avoids the class of bugs where an optimistic update has to be rolled back on failure.
- The failed-save error message is generic (the underlying `ApiError`'s message, or a fallback string) — no error-code-specific messaging yet, since there is no validation step producing structured errors to distinguish.

## Sprint 12 — Validation ✅

Implements the "Validate" gate described in `docs/DATABASE.md`, per an explicit architectural instruction: validation is split into two independent layers that share no business logic — frontend UX validation (instant feedback, generic, reusable) and backend canonical validation (the actual source of truth). Nothing here changes `status` or moves a row toward Review — that transition still doesn't exist.

- **Backend**: new `api/app/validation/` package, deliberately generic so it isn't a Venue-only concept:
  - `schemas.py` — `FieldError {field, message}` and `ValidationResult {valid, errors}`. One reusable response contract; a future `validate_destination()` returns the exact same shape.
  - `venues.py` — `validate_venue(venue)`, the **canonical** rule set and the only place these rules are enforced: `name` non-blank, `category` in the documented `VENUE_CATEGORIES` (already DB-enforced by a `CHECK` constraint, but re-checked here for a structured error instead of a raw constraint violation), and `latitude`/`longitude` within the observed North Coast range (`[30.6, 31.1]` / `[28.6, 29.4]`) — a sanity bound per `DATABASE.md`, not a DB constraint.
  - New route `POST /venues/{venue_id}/validate` (`api/app/api/routes/venues.py`) — reads the venue's **currently persisted** row (not a request body — there's nothing to submit) and returns its `ValidationResult`. Read-only, `404` on an unknown id. Added `POST` to the CORS `allow_methods`.
  - Save Draft (`PATCH /venues/{venue_id}`) is **unchanged** — it still accepts anything Pydantic's type coercion allows, no business-rule enforcement. This is deliberate, not an oversight: `docs/DATABASE.md` frames Validate as a distinct workflow step between Save Draft and Review, not something Save Draft itself gates on — a draft is allowed to be incomplete.
- **Frontend, generic layer** (`src/lib/validation.ts`): `isRequired`, `isWithinMaxLength`, `isValidUrl`, `isValidDecimal`, and a `runFieldRules(value, rules)` combinator — entity-agnostic primitives with no opinion about what makes a *venue* valid, so any future entity's edit form reuses them without touching this file.
- **Frontend, venue-specific field selection** (`features/venues/venueValidation.ts`): `validateVenueDraft(venue)` applies the generic primitives to specific fields — `name` required, `short_description`/`internal_notes` length-capped, `website`/`maps_url` URL-shaped, `latitude`/`longitude` numeric-shaped. Deliberately excludes category membership and geographic coordinate bounds — those are business rules, and duplicating them here would mean two sources of truth for the same rule, which the architectural instruction explicitly ruled out.
- **Inline field errors**: `FieldLabel` gained an `error?` prop (renders red text under the input); a new `fieldStyles.ts` (extracted out of `FieldLabel.tsx` to avoid a react-refresh lint warning from mixing component and non-component exports) provides `fieldInputClassName(hasError)` for the red-border state. `TextField`/`TextAreaField` accept an `error?` prop; `SelectField`/`CheckboxField` don't, since nothing validated this sprint uses them. Every workspace section (`BasicInfoSection`, `LocationSection`, `ContactSection`, `PublishingStatusSection`) now accepts an `errors?: FieldErrors` prop and threads the relevant key to each field.
- **Save Draft gating**: `VenueWorkspace` computes `fieldErrors = validateVenueDraft(displayedVenue)` while in Edit Mode and disables Save Draft whenever any exist, alongside the existing `!isDirty || isSaving` conditions — per "enable/disable Save Draft" being an explicit frontend-validation responsibility.

**How Sprint 11 and 12 fit together**: Save Draft (11) persists whatever the user has, no questions asked. Validate (12) is a separate, non-destructive check anyone can run against what's already saved, without needing to have edited anything. Review (not yet built) would be the step that actually *acts* on a passing `ValidationResult` by moving `status` from `draft` to `review` — this sprint deliberately stops at reporting valid/invalid, since building the status transition wasn't part of the instruction and doing so would have coupled two independently-useful pieces (a query and a mutation) into one.

- Validate has no UI trigger for the case where a user wants to see what's wrong *while* mid-edit — it's disabled until they save first. A future iteration could let Validate run against the in-progress draft (not just the persisted row) by sending it as a request body instead of reading the DB row, but that would blur the line between "is the saved row valid" and "is this hypothetical edit valid," which felt like scope creep against this sprint's specific instruction.
- No endpoint or UI exists yet to act on a passing validation (i.e., actually move `status` from `draft` to `review`) — that's Review, still unbuilt, and deliberately out of scope here.
- `validate_venue`'s category check is currently unreachable in practice (the DB's own `CHECK` constraint would already reject an invalid category before a row could ever be persisted with one) — kept anyway because `DATABASE.md` explicitly lists it as part of the Validate gate's rule set, and because it's the pattern a future field *without* a DB-level constraint would need.

## Sprint 13 — Editorial Readiness ✅

Evolves Sprint 12's Validate response into a richer **Editorial Readiness** model, per explicit architectural instruction. Same endpoint, same "checks the persisted draft, not unsaved edits" behavior confirmed unchanged in the prior conversation — this sprint only grows the response shape and derives one new field from the existing rules. No Review, Approval, Publish, or Revision handling.

- **Backend** (`api/app/validation/schemas.py`): `ValidationResult` gained `ready_for_review: bool`, `warnings: list[FieldError] = []`, and `info: list[FieldError] = []`. Added `build_validation_result(errors, warnings=None, info=None)` — the single place `valid`/`ready_for_review` are derived from a rule set's findings, so every entity's validator (`validate_venue`, and any future `validate_destination`) shares one derivation instead of reimplementing it. For now, `ready_for_review` is simply `valid` (no rule yet makes a warning block readiness) — the "don't invent complex business rules" instruction taken literally.
- **`validate_venue()`** (`api/app/validation/venues.py`) is otherwise **unchanged** — same three error rules (required `name`, `category` membership, coordinate range) — and now returns `build_validation_result(errors)` instead of constructing `ValidationResult` directly. No new warnings/info producers exist yet; the extension points are wired up and empty.
- **Route unchanged**: `POST /venues/{venue_id}/validate` still takes no body, still reads the persisted row, still returns `404` for an unknown id. Kept the endpoint exactly per instruction — no rename, since the added fields are purely additive to an already-correctly-named route.
- **Frontend types** (`src/types/validation.ts`): `ValidationResult` mirrors the four new/changed fields exactly.
- **`ValidationSummary.tsx`** rewritten to render the full model: a top-level "Ready for review." / "Not ready for review." banner driven by `ready_for_review` (not `valid` — kept as two conceptually distinct fields even though numerically equal today, since the UI shouldn't silently conflate them), followed by separate error (red), warning (amber), and info (blue) sections, **each rendered only when its array is non-empty** — so `warnings`/`info` staying empty today needs no placeholder or "coming soon" UI, and no future change is needed when a real rule starts populating them.
- Verified against the real Supabase-backed API and in-browser: `curl`'d the endpoint directly for both a valid venue (`{valid: true, ready_for_review: true, errors: [], warnings: [], info: []}`) and a temporarily out-of-range latitude (`{valid: false, ready_for_review: false, errors: [...]}`, reverted after); confirmed `404` still returned for an unknown id. In-browser: the valid venue shows a clean "Ready for review." banner with no empty error/warning/info boxes; forcing the same out-of-range latitude (via Edit → Save Draft, since Validate still checks the persisted row) and clicking Validate shows "Not ready for review." plus the existing red error box — same wording pattern as Sprint 12, now framed around readiness. Re-verified the Sprint 12 frontend field-level checks (clearing Name shows an inline error and disables Save Draft) still work — no regression. Database restored to the exact Sprint 4 seed state after verification. Build and lint clean, no console errors.

**Why Editorial Readiness is separate from Review**: Review is a stateful transition (`draft → review`, a real database write, presumably a human decision). Editorial Readiness is a stateless question — "would this row qualify for Review right now?" — answerable at any time with zero side effects, which is exactly what `POST /venues/{id}/validate` already was in Sprint 12. Keeping them distinct means readiness can be checked repeatedly without risk of accidentally mutating `status`, and means Review (whenever built) doesn't need its own copy of the business rules — it consumes this endpoint's answer instead of re-deriving it. See `docs/API.md`'s new "Editorial Readiness" subsection for the full reasoning, including how Review will consume `ready_for_review` as a precondition and how Publish's `approved`-only eligibility transitively depends on it.

**Technical debt / follow-ups noted, not fixed this sprint**:
- No warning- or info-producing rule exists yet anywhere in `validate_venue()` — `warnings`/`info` are proven-out extension points, not yet exercised by a real check. The next entity or field that needs a non-blocking notice (e.g. "no cover image set") is the natural first real use.
- `ready_for_review` and `valid` are computed identically today (`ready_for_review = valid`), which could read as redundant until a warning-blocks-readiness rule actually exists — kept as two separate fields anyway per the explicit instruction that they're distinct concepts, and because the frontend already treats them as distinct (the banner reads `ready_for_review`, not `valid`).
- Same limitation carried over from Sprint 12: Validate still can't be run against unsaved edits, only the persisted row — reconfirmed as intentional, not revisited this sprint.

## Sprint 14 — Review Workflow ✅

The first editorial state transition: `venues.status` moves `draft → review`. Nothing else — no Approval, Publish, or Rollback.

- **Backend** (`api/app/api/routes/venues.py`): new `POST /venues/{venue_id}/submit-for-review`, no request body, acts on the venue's persisted row. Rejects rather than transitioning unconditionally:
  - `404` if the venue doesn't exist (existing pattern).
  - `409` (`error: "invalid_transition"`) if `status != 'draft'` — covers "already in review," "already approved," and "archived" the same way, since none of them can re-enter `draft → review`.
  - `422` (`error: "not_ready_for_review"`) if `status == 'draft'` but `validate_venue()` says `ready_for_review` is `false` — the response includes the same structured `errors` list Editorial Readiness already produces.
  - On success: sets `status = 'review'`, commits, returns the updated venue as `VenueOut` (same shape as `GET`/`PATCH`). This is the only code path in the entire codebase that writes `venues.status`.
  - **Reuses `validate_venue()` unchanged** as the precondition rather than re-deriving readiness — Review is an editorial *action*, Validate remains a read-only *check*; the route composes them instead of merging them. No schema change needed — `venues.status` already permits `'review'` per the Sprint 3 CHECK constraint.
- **Frontend**: `apiClient.ts`'s `apiPost` gained structured-error-message extraction (`extractErrorMessage`) so a `409`/`422`'s `detail.message` surfaces instead of a generic "failed with status N" — a small, broadly-applicable improvement, not Review-specific. `api.ts` gained `submitVenueForReview(id)`; a new `useSubmitForReview` mutation hook follows the same cache-update pattern as `useUpdateVenue`/`useValidateVenue`.
- **`WorkspaceToolbar`** gained a green "Submit for Review" button, conditionally *rendered* (not just disabled) only when `!isDirty && venue.status === 'draft' && validationResult?.ready_for_review === true` — computed in `VenueWorkspace` from the actual `ValidationResult` state a prior Validate call produced, never re-derived independently, so the button can't show "ready" without the backend having just said so. On success, reuses `useDraft`'s existing `commitSave` (from Sprint 11) to refresh the displayed venue with the server's response, and clears the now-stale `validationResult`.
- Verified against the real Supabase-backed API (temporarily flipping the seeded venue's `status` to `draft` via a direct DB session, since no endpoint allows setting status arbitrarily — by design) and in-browser:
  - **draft → review**: `curl`'d directly — `200` with `status: "review"` in the response.
  - **already review**: repeating the same call — `409` with `current_status: "review"` in the structured detail.
  - **invalid draft**: blanked the name via direct DB write, attempted submit — `422` with `errors: [{"field": "name", "message": "Name is required."}]`.
  - **not ready** (a second, distinct rule): PATCHed latitude out of range, attempted submit — `422` with the matching latitude error. Confirmed `status` stayed `draft` throughout every rejected attempt — the transition really is all-or-nothing.
  - **unknown venue**: `404`, `{"detail": "Venue not found"}`.
  - **In-browser**: set `draft`, clicked Validate (saw "Ready for review." + the "Submit for Review" button appear), clicked Submit for Review, confirmed the list panel's badge and the Publishing Status section's `STATUS` field both updated to "Review" — and reconfirmed after a hard page reload, proving it's a real persisted transition, not a client-side illusion.
  - Database restored to the exact Sprint 4 seed state (`status: approved`) after every test. Build and lint clean, no console errors.

Diagnosed before touching any code: TCP reachability to the pooler was fine, the `.env` was byte-identical to what worked in Sprints 11–13, and the project's own direct-connection hostname (`db.<project-ref>.supabase.co`) returned `NXDOMAIN` — pointing at the Supabase project itself being paused, not a local misconfiguration. **Why Review is the first workflow transition**: of the three status changes ahead (`draft → review`, `review → approved`, and eventually Publish), `draft → review` is the only one whose precondition already existed in full — Sprint 13's `ready_for_review`. Approval implies reviewer identity/notes the schema doesn't model yet (and auth doesn't exist yet to identify who's approving); Publish is a whole-dataset snapshot operation, not a single-row transition. Building `draft → review` first establishes the pattern (fetch row → check precondition → reject with structured error or write `status`) every later transition will reuse, using the one precondition that was already fully built.

**Why Approval remains separate**: `review → approved` is a distinct real-world decision (a human reviewer's judgment call) from Editorial Readiness (an automatable check), and will need its own precondition (`status == 'review'`) and, once auth exists, its own actor/notes fields — none of which belongs bolted onto this endpoint as an "and approve it too" flag. Keeping every stage of `docs/DATABASE.md`'s four-stage workflow as its own action, built when it's actually in scope, avoids collapsing two different decisions into one.

**Technical debt / follow-ups noted, not fixed this sprint**:
- No endpoint or UI exists yet for Approval (`review → approved`) — deliberately out of scope, per instruction.
- `submit-for-review`'s `409` response treats every non-`draft` status identically (`review`, `approved`, `archived` all produce the same `invalid_transition` shape, just a different `current_status` value) — sufficient for now since there's only one valid transition to guard; a richer per-status message could be added if/when more transitions exist and a `422`/`409` starts needing to explain more nuance.
- `apiPost`'s new structured-error-message extraction is generic and already benefits Validate's error path too (previously untested against a real backend rejection, since Validate never fails with a 4xx) — noted as a quiet improvement, not a scope expansion, since it required no new endpoint-specific code.
